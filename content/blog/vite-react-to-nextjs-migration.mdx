This is a Vite React to Next.js migration I did on my own portfolio, hamzatariq.site. The site looked good but Google could barely read it. After moving it to Next.js 15, the mobile Lighthouse SEO score went from 83 to 100 and the home page Largest Contentful Paint (LCP) dropped from 18.0 s to 2.6 s, without giving up the 3D character or the animations.

Below are the steps, the problems I hit, and what I'd tell anyone who wants to migrate Vite to Next.js the same way.

## The starting point: a fast-looking site Google couldn't read

The site was a Vite + React single-page app. To a visitor on a good phone it looked finished. To a search engine it was almost empty:

- **Every URL returned the same nearly empty HTML file.** All content was built in the browser by JavaScript.
- **One hard-coded title for every page.** No meta description at all.
- **No sitemap, no robots.txt, no structured data.**
- **A slow first screen.** On mobile, the home page took 18.0 s to show its main content, because the 3D character and the preloader blocked it.

I explain why this hurts rankings in more detail in [why a React website is not ranking on Google](/blog/react-website-not-ranking-on-google). The short version: crawlers that don't run JavaScript see nothing, and Google sees the same title on every page.

## Why I chose Next.js instead of patching Vite

I could have added a prerender plugin and react-helmet to the Vite app. I didn't, for three reasons:

1. **Real HTML for every page.** [Next.js](https://nextjs.org/docs/app/guides/migrating/from-vite) pre-renders each route as static HTML, so the first response already contains the content.
2. **Metadata in the server HTML.** Each page exports its own title, description, canonical URL and social image. No script has to run first.
3. **Built-in image and font optimization.** `next/image` and self-hosted fonts handle two of the biggest LCP problems.

It's still React, so my components moved over almost unchanged. For me, Vite vs Next.js for SEO came down to that first point: what the server sends before any JavaScript runs.

## Does the official Next.js migration guide fix SEO?

Not on its own. The [official guide](https://nextjs.org/docs/app/guides/migrating/from-vite) is written to get you onto Next.js quickly, so its first stage keeps your app as a client-side single-page app: Next.js serves one shell, and React Router still builds every page in the browser. That is a sensible way to start, but a crawler that doesn't run JavaScript still gets an empty page, and every URL still shares one title.

The SEO gains only come in the next stage, which the guide leaves to you: moving each route into the App Router so it's pre-rendered as HTML, and giving each page its own metadata. That's the part this post is about.

<MyTake>
If search traffic is the reason you're migrating, I recommend going straight to pre-rendered routes for every public page and keeping the SPA shell only for parts behind a login. Stopping after the guide's first stage gives you a new framework but changes almost nothing for Google.

For a site with a handful of pages, I move everything in one go. For a large app, I move the pages that should rank first (home, services, products) and leave the logged-in screens for later.
</MyTake>

## Step by step: the Vite React to Next.js migration

### 1. Move pages into the App Router

Each React Router route became a folder in `src/app/`. The home page became `src/app/page.tsx`, project pages became one dynamic route, `src/app/work/[slug]/page.tsx`, with `generateStaticParams` returning every project slug so all of them are built ahead of time.

```tsx
// src/app/work/[slug]/page.tsx
export const generateStaticParams = () => PROJECTS.map((p) => ({ slug: p.slug }));

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { slug } = await params;
  const project = getProject(slug);
  return {
    title: project.title,
    description: project.summary,
    alternates: { canonical: `/work/${slug}` },
  };
}
```

### 2. Give every page its own metadata

Every route exports `metadata` or `generateMetadata`: a unique title, a 150–160 character description and a canonical URL. I wrote small helpers that keep titles short enough and descriptions within that range, so new pages can't ship with bad metadata.

### 3. Load browser-only code on the client

This was the biggest risk. GSAP ScrollSmoother, the Three.js character and the tech-stack scene all need `window`. In Next.js they would crash during pre-rendering.

The fix: load them with `next/dynamic` and `ssr: false`, inside a client component.

```tsx
"use client";
import dynamic from "next/dynamic";

const Character = dynamic(() => import("./Character"), { ssr: false });
```

The page HTML (headings, text, links, project list) is rendered on the server. The 3D and animation layers start in the browser after that.

### 4. Add the files search engines look for

Next.js generates them from code:

- `src/app/sitemap.ts` lists every page, including the 31 project pages.
- `src/app/robots.ts` allows crawling and points to the sitemap.
- JSON-LD structured data on every page: a `Person` on the home page, and breadcrumbs and project details on inner pages.
- A generated social preview image for every page type, so links shared on WhatsApp or LinkedIn show a proper card.

### 5. Fix the first screen

The preloader and the 3D model were the main reasons for the 18.0 s LCP. I made sure the real content renders first, moved images to `next/image`, and self-hosted the Geist font so text doesn't wait for a font server.

### 6. Tell search engines after each deploy

I set up IndexNow, so Bing and other engines that support it hear about new and changed pages automatically after every production deploy.

## What went wrong (and how I fixed it)

No migration is perfectly smooth. These were my real problems:

- **"window is not defined" errors.** Any library that touches the browser during import breaks pre-rendering. Moving it behind `next/dynamic` with `ssr: false` fixed every case.
- **Animation state leaking between pages.** ScrollSmoother and WebGL kept running after leaving the home page. I made links into and out of the home page full page loads, so each page starts clean.
- **Styles loading in a different order.** A few CSS rules depended on import order in Vite. I moved page styles next to the components that use them.
- **Hard-coded facts in many places.** The email, social links and site URL were repeated across files. I moved them into one file, so the metadata, the structured data and the footer can't disagree.

## How to plan your own migration

Most of the risk when you convert a React app to Next.js is decided before the first line of code. This is the plan I'd write for any Vite or Create React App site:

1. **Measure first.** Run mobile Lighthouse on the home page and two or three inner pages, and save the scores. Without a "before", you can't prove the "after".
2. **List every route.** Write down every URL the site has today, including dynamic ones like product or project pages. Each one needs a home in the new app.
3. **Find the browser-only code.** Search for `window`, `document`, `localStorage`, animation libraries, maps, charts and 3D. Each of these will need to load on the client.
4. **Decide what is static.** Pages that are the same for every visitor (most marketing pages) should be pre-rendered at build time. Only pages that depend on the visitor need server rendering on each request.
5. **Plan the metadata.** For each page, write the title, the description and the main thing it should rank for. One page, one main search term.
6. **Keep the URLs.** Use the same paths in the new app. Where a path has to change, add a permanent redirect.
7. **Measure again before launch.** Run the same Lighthouse tests on a production build and compare.

The last step is where many migrations stop too early. A development server is slower than production and gives misleading scores, so always test the real build. All my numbers in this post come from a local production build, measured the same way before and after.

## Should you migrate your site?

Migrate if:

- Your React site needs search traffic or leads and isn't getting either.
- View source on your pages shows an empty root `div`.
- Every page shares the same title.

- Links to your site shared on WhatsApp or LinkedIn show no title or image.
- You plan to add a blog, service pages or other content you want people to find on Google.

The last point is easy to overlook. A blog on a client-rendered React app gives you very little, because every post has the same empty HTML and the same title. On Next.js, every new post is a real page with its own metadata from the day you publish it. That's how the blog on this site works: each post is pre-rendered, added to the sitemap and sent to search engines automatically.

You probably don't need to if your app is behind a login (dashboards, internal tools). Search engines can't see those pages anyway.
